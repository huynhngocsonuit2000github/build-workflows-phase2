## 4. Phần A · `s0b-1`: test

### 4.1 Cấu trúc

```
apps/tasklite/
  TaskLite.slnx                       # thêm project test
  tests/TaskLite.Tests/
    TaskLite.Tests.csproj             # xUnit, Microsoft.AspNetCore.Mvc.Testing, tham chiếu TaskLite.Api
    TaskLiteFactory.cs                # WebApplicationFactory<Program>
    ProjectEndpointsTests.cs
    TaskEndpointsTests.cs
    HealthTests.cs
```

- Tạo bằng `dotnet new xunit`, rồi `dotnet sln TaskLite.slnx add tests/TaskLite.Tests`. Target `net10.0`, bật `Nullable`.
- `TaskLiteFactory`: môi trường `Testing`; đổi `ConnectionStrings:DefaultConnection` sang một file SQLite tạm **riêng cho mỗi instance** (ví dụ `Path.Combine(Path.GetTempPath(), $"tasklite-test-{Guid.NewGuid():N}.db")`); xóa file khi dispose (gọi `SqliteConnection.ClearAllPools()` trước khi xóa, nếu không Windows báo file đang bị khóa).
- Mỗi test tự tạo dữ liệu nó cần qua API (tạo project, tạo task), không dựa vào dữ liệu seed, không dựa vào thứ tự chạy, không dùng chung DB giữa các test. Có thể viết vài helper nhỏ (`CreateProjectAsync(user, name, members)`, `CreateTaskAsync(...)`, `Client(userId)`).
- Đọc response bằng `ReadFromJsonAsync` với DTO có sẵn trong `Endpoints/Contracts.cs` (hoặc `JsonDocument` khi kiểm tra ProblemDetails). Nhớ enum dạng chuỗi.
- Tên test: `Method_Scenario_ExpectedResult`, ví dụ `CreateTask_EmptyTitle_Returns400WithTitleError`.

### 4.2 Danh sách test tối thiểu

Plan yêu cầu 5 nhóm tình huống: thành công, lỗi, timeout, trùng, không có quyền. TaskLite không gọi dịch vụ ngoài nên **không có timeout**: ghi rõ điều này trong README phần test, không viết test giả.

| Nhóm | Test |
|---|---|
| Thành công | Tạo project → 201, có `Location`, người tạo nằm trong `memberIds` · Liệt kê project chỉ thấy project mình là thành viên · Tạo task → 201, `status` = `Todo`, có `Location` · Liệt kê task sắp theo `id` tăng dần · Đọc một task · Đổi status sang `InProgress` rồi `Done` → 200 và đọc lại thấy đúng · `GET /health` → 200 `{ "status": "ok" }` không cần header |
| Lỗi đầu vào | Title rỗng hoặc chỉ khoảng trắng → 400 có `errors.title` (chấp nhận `title` hoặc `Title`) · Title 201 ký tự → 400 · Tên project rỗng → 400 · Assignee không phải thành viên → 400 · Status `Archived` → 400 · Status `"1"` → 400 (hồi quy 0.2) · Body JSON hỏng → 400 |
| Không tồn tại | Project không tồn tại → 404 · Task thuộc project khác → 404 |
| Không có quyền | Thiếu `X-User-Id` → 401 · `X-User-Id` chỉ có khoảng trắng → 401 · Người ngoài (`mallory`) đọc project, đọc danh sách task, tạo task, đổi status → 403 · `ALICE` đọc project của `alice` → 403 và liệt kê → trống (hồi quy 0.1) |
| Trùng | `memberIds` có phần tử trùng (và trùng với người tạo) → lưu một lần · Tạo hai task cùng title → cả hai 201, khác `id` (hệ thống chưa có idempotency, test ghi lại hành vi hiện tại) |
| Dữ liệu | `createdAt` của task lúc tạo và lúc đọc lại bằng nhau và kết thúc bằng `Z` (hồi quy 0.3) |
| Lỗi trả về | 401, 403, 404 đều có body ProblemDetails (`Content-Type: application/problem+json`, có `status`, `title`) |

Có thể thêm test nếu thấy cần, nhưng đừng test lại framework (ví dụ không test xUnit hay EF Core).

## 5. Phần B · `s0b-2`: Docker và Compose

### 5.1 File

```
apps/tasklite/
  .dockerignore                         # bin/, obj/, tests/, *.db*, TestResults/, .vs/, node_modules/
  src/TaskLite.Api/Dockerfile
  web/Dockerfile
  docker-compose.yml
```

Build context của cả hai image là `apps/tasklite/` (để Dockerfile API thấy được `.slnx` nếu cần và `.dockerignore` có hiệu lực).

### 5.2 API image

- Multi-stage: stage build `mcr.microsoft.com/dotnet/sdk:10.0` (`dotnet restore` riêng trước để tận dụng cache layer, rồi `dotnet publish -c Release -o /app`); stage chạy `mcr.microsoft.com/dotnet/aspnet:10.0-alpine` (có sẵn `wget` cho healthcheck; Debian image không có `curl`/`wget`).
- Chạy bằng user không phải root (`USER $APP_UID`, có sẵn trong image). Trước đó tạo thư mục `/data` và `chown` cho `$APP_UID` để SQLite ghi được.
- Container lắng nghe cổng 8080 (mặc định của image .NET), compose map ra 5200.
- Nếu SQLite báo thiếu thư viện native trên alpine, ghi lại cách xử lý trong báo cáo.

### 5.3 Web image

- `nginx:alpine`, copy `index.html`, `app.js`, `config.json` vào `/usr/share/nginx/html`.
- `config.json` phải **đổi được lúc chạy, không build lại image** (bài học phase 1): compose mount một file `config.json` vào đè lên file trong image. Với máy local, nội dung vẫn là `{ "apiBaseUrl": "http://localhost:5200" }` vì trình duyệt gọi API từ máy host.

### 5.4 Compose

`apps/tasklite/docker-compose.yml`, project name `tasklite`:

| Service | Image build | Cổng | Cấu hình |
|---|---|---|---|
| `api` | `src/TaskLite.Api/Dockerfile` | `5200:8080` | `ConnectionStrings__DefaultConnection=Data Source=/data/tasklite.db`, `Seed__DemoData=true`, `Cors__AllowedOrigins__0=http://localhost:4300`; named volume `tasklite-data:/data`; healthcheck `wget -qO- http://localhost:8080/health` (interval 10s, timeout 3s, retries 5, start_period 10s) |
| `web` | `web/Dockerfile` | `4300:80` | Mount `./web/config.json` vào `/usr/share/nginx/html/config.json` (read-only); `depends_on: api` với `condition: service_healthy` |

Không dùng `ASPNETCORE_ENVIRONMENT=Development` trong compose (phần 0.4 đã cho phép migrate và seed mà không cần Development).

## 6. Phần C · `s0b-3`: CI

### 6.1 Workflow

File `.github/workflows/tasklite-ci.yml` ở **gốc repo** (GitHub chỉ đọc workflow ở đây).

- Tên workflow `tasklite-ci`. Chạy khi `pull_request` và `push` vào nhánh `main`, chỉ khi có thay đổi trong `apps/tasklite/**` hoặc chính file `.github/workflows/tasklite-ci.yml`.
- `defaults.run.working-directory: apps/tasklite`. `permissions: contents: read`. `concurrency` hủy lần chạy cũ của cùng PR.
- Job `build-test` (tên job này sẽ được chọn làm required check, **không đổi tên** sau này), `runs-on: ubuntu-latest`, `timeout-minutes: 15`:
  1. `actions/checkout@v4`
  2. `actions/setup-dotnet@v4` với `dotnet-version: 10.0.x`
  3. `dotnet restore TaskLite.slnx`
  4. `dotnet build TaskLite.slnx --no-restore -c Release -warnaserror`
  5. `dotnet test TaskLite.slnx --no-build -c Release --logger trx --results-directory TestResults` (nếu project test dùng Microsoft.Testing.Platform thì dùng tùy chọn TRX tương đương, ghi lại trong báo cáo)
  6. `actions/upload-artifact@v4` tải `apps/tasklite/TestResults/**/*.trx` lên, tên `test-results`, **chạy cả khi test fail** (`if: always()`)
- Job `docker-build`, `needs: build-test`: `docker build` hai image (không push, không đăng nhập registry).

### 6.2 Lưu ý về đường dẫn trên Linux

CI chạy trên Linux: tên file phân biệt hoa thường, đường dẫn dùng `/`. Kiểm tra mọi đường dẫn trong `.csproj`, `.slnx`, Dockerfile khớp đúng hoa thường với tên thư mục thật.

## 7. Kiểm tra trước khi báo xong

Chạy thật và ghi output vào báo cáo. Dừng mọi tiến trình đang chiếm cổng 5200, 4300 trước khi chạy (ví dụ API từ `dotnet run` còn sót).

1. `dotnet build TaskLite.slnx -warnaserror` trong `apps/tasklite`: 0 error, 0 warning.
2. `dotnet test TaskLite.slnx` **hai lần liên tiếp**: cùng số test, tất cả pass cả hai lần. Ghi tổng số test và thời gian.
3. Chứng minh test bắt được lỗi: tạm sửa code để người ngoài không còn bị 403 (ví dụ bỏ kiểm tra thành viên ở một endpoint), chạy `dotnet test`, thấy test fail, ghi tên test fail; rồi **hoàn lại** code và chạy lại cho pass. Không commit thay đổi tạm này.
4. Không còn file `tasklite-test-*.db` sót lại trong thư mục temp sau khi chạy test.
5. `docker compose up -d --build` trong `apps/tasklite`, rồi:
   - `docker compose ps`: `api` ở trạng thái `healthy`, `web` đang chạy.
   - `curl http://localhost:5200/health` → 200.
   - `curl -H "X-User-Id: alice" http://localhost:5200/projects` → thấy project `Demo`.
   - Mở `http://localhost:4300`, tạo một task, thấy nó trong bảng (chụp màn hình nếu được).
   - `docker compose down` rồi `docker compose up -d`: task vừa tạo **vẫn còn** (volume giữ dữ liệu).
   - Sửa `apiBaseUrl` trong `web/config.json` thành một địa chỉ sai, `docker compose restart web`, thấy trang báo lỗi gọi API (chứng minh config đổi được lúc chạy, không build lại); rồi hoàn lại.
   - `docker compose down` khi xong (giữ volume).
6. CI: chưa chạy được vì repo chưa có trên GitHub. Kiểm tra YAML hợp lệ (ví dụ `npx --yes yaml-lint .github/workflows/tasklite-ci.yml` hoặc công cụ tương đương), và chạy tay đúng các lệnh của job `build-test` (bước 3–5 ở mục 6.1) trong `apps/tasklite` để chắc chắn chúng chạy được, có file `.trx` sinh ra.
